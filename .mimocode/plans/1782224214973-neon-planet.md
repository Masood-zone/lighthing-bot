# Plan: Reschedule Phase Fix + Admin UI Headless/Execution Mode Toggles

## Goal

1. Fix the reschedule flow in API mode so the worker correctly navigates to My Appointments, clicks the appointment card, clicks RESCHEDULE/CONFIRM, and enters the date-hunting flow.
2. Add per-user Headless/Browser mode toggle and per-user Execution Mode (API/DOM) toggle to the Admin UI.

---

## Part 1: Fix Reschedule Flow in API Mode

### Problem

The `contextBootstrap.js` `bootstrapAppointmentSurface()` for reschedule mode only navigates to `/home/appointment/myappointment` and waits for an appointment search response. It does **not**:
- Click on the appointment card
- Click the "RESCHEDULE" button
- Handle confirmation dialogs
- Wait for the booking UI to load

The DOM worker (`main/index.js:1087-1199`) does all of this correctly. The API mode needs the same interaction.

### Changes

**File: `backend/src/services/visaApi/contextBootstrap.js`**

Add a `clickRescheduleForCurrentUser()` function (mirroring the DOM worker logic from `main/index.js:1109-1199`):
- Find the RESCHEDULE button on the My Appointments page using selectors: `a.my-app-button-popup-resch`, `a:has-text('RESCHEDULE')`, `button:has-text('RESCHEDULE')`, `[role='button']:has-text('RESCHEDULE')`
- Handle native browser confirm dialogs
- Click the button
- Handle Angular `mat-dialog` confirmation if present
- Wait for the booking UI (`.ofc-book-slot-block`) to become visible
- Accept native dialog confirmations
- Wait for the appointment search API response

Update `bootstrapAppointmentSurface()` for `mode === "reschedule"`:
- After navigating to myappointment, call `clickRescheduleForCurrentUser(page)`
- Handle dialog/confirmation as the DOM worker does
- Wait for the booking block or appointment search response

**File: `backend/main/api-worker.js`**

No changes needed to `api-worker.js` itself — the `bootstrapAppointmentSurface` function is called from `resolveContext()` at line 449, and the mode is already passed correctly.

### Verification

- Run with `VISA_RESCHEDULE=1` and `VISA_EXECUTION_MODE=api`
- Worker should: navigate to myappointment → click RESCHEDULE card → handle confirm → enter date hunting flow
- API calls should follow the standard sequence: getuser → getFirstAvailableMonth → getSlotDates → getSlotTime → submitRescheduleAppointment (PUT)

## Part 2: Add Per-User Headless/Browser Toggle to Admin UI

### Problem

The `update-user.tsx` form (line 154) strips `headless` from edit submissions:
```ts
delete (patch as Partial<CreateUserInput>).headless;
```

The backend already accepts `headless` in both create and update routes. The worker pool already passes `VISA_HEADLESS` from `session.config.headless`.

### Changes

**File: `frontend/src/pages/admin/users/update-user.tsx`**

1. Add `headless` to the form default values:
   - Create defaults: `headless: false`
   - Edit defaults: `headless: initial?.config?.headless ?? false`

2. Add a Headless Mode toggle field (similar to the Reschedule Mode field):
   - Use a `Select` with "Yes"/"No" options
   - Description: "When set to Yes, the browser runs headless (invisible). Set to No to see the browser window."

3. Remove the `delete (patch as Partial<CreateUserInput>).headless;` line from the form submit handler so `headless` is sent to the backend.

**File: `frontend/src/services/users/users.types.ts`**

No changes needed — `headless` is already in `BotUser.config` and `CreateUserInput`.

### Verification

- Create a new user with Headless = No → worker should launch visible browser
- Edit an existing user to toggle Headless → next session should reflect the change
- Check `data/store.json` to confirm `headless` is persisted

## Part 3: Add Per-User Execution Mode Toggle to Admin UI

### Problem

`VISA_EXECUTION_MODE` is currently a server-level env var. The worker pool passes it at `workerPool.js:721-722`:
```js
VISA_EXECUTION_MODE: process.env.VISA_EXECUTION_MODE || process.env.VISA_WORKER_MODE || "api",
```

The user wants each user to independently choose API or DOM mode.

### Changes

**File: `frontend/src/services/users/users.types.ts`**

Add `executionMode` to the types:
```ts
executionMode?: "api" | "dom";
```
Add to `BotUser.config`, `CreateUserInput`, and `UpdateUserInput`.

**File: `frontend/src/pages/admin/users/update-user.tsx`**

1. Add `executionMode` to form defaults:
   - Create defaults: `executionMode: "api"`
   - Edit defaults: `executionMode: initial?.config?.executionMode ?? "api"`

2. Add an Execution Mode field:
   - Use a `Select` with "API" / "DOM" options
   - Description: "API mode uses backend-only authenticated requests. DOM mode uses legacy Playwright element interaction."

3. Include `executionMode` in the form submission (no stripping).

**File: `backend/src/routes/users.js`**

1. Accept `executionMode` in create route (line 166-177):
   - Validate: must be "api" or "dom" if provided, default "api"

2. Accept `executionMode` in update route (line 329-338):
   - Validate same as create

3. Pass `executionMode` to `store.createSession()` and `store.updateSession()`.

**File: `backend/src/queue/workerPool.js`**

Update `_startSession()` (line 721-722) to use per-user execution mode:
```js
VISA_EXECUTION_MODE: session.config.executionMode || process.env.VISA_EXECUTION_MODE || process.env.VISA_WORKER_MODE || "api",
```

**File: `backend/src/routes/users.js` — `sanitizeUser()`**

Ensure `executionMode` is included in the sanitized output (it's part of config, so it should flow through automatically).

### Verification

- Create user with executionMode = "dom" → worker should load `main/index.js` (DOM flow)
- Create user with executionMode = "api" → worker should load `main/api-worker.js` (API flow)
- Edit user to switch modes → next session uses the new mode
