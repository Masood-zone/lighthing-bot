# Plan: Replace Browser Automation with Direct API Calls

## Goal
Replace Playwright/Selenium browser automation with direct HTTP API calls to usvisaappt.com for faster, more reliable visa appointment booking. The new worker will use the same IPC protocol so the worker pool, frontend, and desktop app require minimal changes.

---

## Current Architecture (What We're Replacing)

```
Frontend → REST API → WorkerPool.fork(workerEntry.js) → Playwright/Selenium browser
                                                         ↕ IPC (status/log messages)
                                              WorkerPool updates session state
```

- **Worker entry**: `backend/src/workerEntry.js` → `backend/main/index.js` (Playwright)
- **Worker pool**: `backend/src/queue/workerPool.js` — forks child processes, passes env vars, handles IPC
- **IPC protocol**: Workers send `{type: "status", state, message}` and `{type: "log", level, message}`
- **Config via env**: `VISA_PLATFORM_URL`, `VISA_USER_EMAIL`, `VISA_USER_PASSWORD`, `VISA_PICKUP_POINT`, `VISA_HEADLESS`, `VISA_RESCHEDULE`, date range vars, proxy vars

## Target Architecture

```
Frontend → REST API → WorkerPool.fork(api-worker.js) → HTTP client → usvisaappt.com API
                                                         ↕ IPC (status/log messages — same protocol)
                                              WorkerPool updates session state (unchanged)
```

---

## Implementation Steps

### Step 1: Create the API Client Module
**File**: `backend/main/api-client.js` (new)

A reusable HTTP client for the usvisaappt.com platform API. This module encapsulates:
- **Authentication**: Login flow, token/session management, cookie jar
- **Calendar/Availability**: Fetch available dates for a given month and pickup point
- **Time Slots**: Fetch available time slots for a selected date
- **Booking Submission**: Submit the appointment booking request
- **Reschedule**: Submit reschedule request for existing appointment
- **Proxy support**: Route requests through configured proxy (HTTP/HTTPS)
- **Retry logic**: Handle transient errors, rate limits, session expiry

The user will provide the actual endpoint URLs, request formats, and auth flow details separately. This module will be designed with clear function signatures that accept standard parameters so it can be easily updated once the exact API specs are confirmed.

**Key functions** (to be filled in with actual API details):
```js
class VisaApiClient {
  constructor({ email, password, loginUrl, proxyUrl }) {}
  async login() {}           // Returns auth token/session
  async checkAvailability(month, year, pickupPoint) {}  // Returns available dates
  async getTimeSlots(date, pickupPoint) {}               // Returns available slots
  async bookAppointment(date, timeSlot, pickupPoint) {}  // Returns booking result
  async rescheduleAppointment(date, timeSlot) {}         // Returns reschedule result
}
```

### Step 2: Create the API Worker
**File**: `backend/main/api-worker.js` (new)

A new worker entry point that replaces Playwright/Selenium with the API client. It must:
- Read the same env vars as the current workers (`VISA_PLATFORM_URL`, `VISA_USER_EMAIL`, etc.)
- Send the **same IPC messages** as the current workers (`{type: "status", state, message}` and `{type: "log", level, message}`)
- Implement the same booking loop: login → search dates → book → report completion
- Handle the same session states: `LOGIN`, `DASHBOARD`, `SELECT_PICKUP`, `DATE_SELECTED`, `SLOT_SELECTED`, `PROCEED`, `COMPLETED`, `ERROR`, `BLOCKED`

**Booking flow** (API equivalent of the current browser flow):
1. `LOGIN` → Call auth endpoint, get session token
2. `DASHBOARD` → Verify auth succeeded
3. `SELECT_PICKUP` → Set pickup point in session
4. `DATE_SCAN` → Query availability API for each month within date range
5. `DATE_SELECTED` → Found an available date
6. `SLOT_SELECTED` → Query time slots, pick earliest
7. `FINAL_ACTION_CLICKED` → Submit booking
8. `COMPLETED` → Verify booking succeeded

**IPC messages to preserve** (these are consumed by `workerPool.js`):
- `{type: "status", state: "LOGIN", message: "..."}`
- `{type: "status", state: "DASHBOARD", message: "Dashboard detected"}`
- `{type: "status", state: "SELECT_PICKUP", message: "Selecting pickup: Accra"}`
- `{type: "status", state: "DATE_SCAN", message: "Scanning for dates..."}`
- `{type: "status", state: "DATE_SELECTED", message: "2026-07-15"}`
- `{type: "status", state: "SLOT_SELECTED", message: "Time slot selected: 10:30 AM"}`
- `{type: "status", state: "FINAL_ACTION_CLICKED", message: "Booking submitted"}`
- `{type: "status", state: "COMPLETED", message: "Booking confirmed"}`
- `{type: "status", state: "BLOCKED", message: "Access restriction"}`
- `{type: "status", state: "ERROR", message: "Login failed"}`

### Step 3: Update Worker Entry Point
**File**: `backend/src/workerEntry.js` (modify)

Currently hardcodes `require("../main/index")`. Change to select worker based on env var:

```js
const workerMode = process.env.VISA_WORKER_MODE || "api";

if (workerMode === "playwright") {
  require("../main/index");
} else if (workerMode === "selenium") {
  require("../main/visa-bot");
} else {
  require("../main/api-worker");  // default: API mode
}
```

This is a minimal, safe change — existing deployments can set `VISA_WORKER_MODE=playwright` to keep the old behavior.

### Step 4: Update Worker Pool
**File**: `backend/src/queue/workerPool.js` (modify)

**4a.** Pass new env var `VISA_WORKER_MODE` to child processes in `_startSession()` (around line 642-681):
```js
VISA_WORKER_MODE: process.env.VISA_WORKER_MODE || "api",
```

**4b.** The rest of the worker pool is **unchanged** — it already:
- Manages the queue and concurrency limits
- Handles IPC messages from workers
- Maps worker states to session statuses
- Manages proxy assignments
- Sends email notifications on COMPLETED

### Step 5: Add New Environment Variables
**File**: `backend/src/server.js` (modify)

Add configuration for API worker mode:

| Variable | Description | Default |
|----------|-------------|---------|
| `VISA_WORKER_MODE` | Worker mode: `api`, `playwright`, `selenium` | `api` |

The API-specific auth tokens, base URLs, etc. will be configured per-session (already handled via the existing user config fields: `loginUrl`, `email`, `password`).

### Step 6: Frontend Changes (Minimal)
**Files**: No structural changes needed

The frontend already sends all the fields the API worker needs:
- `loginUrl` → API base URL
- `email` → API credentials
- `password` → API credentials  
- `displayName` → User label
- `pickupPoint` → Pickup location
- `reschedule` → Mode toggle
- `dateStart`/`dateEnd`/`daysFromNow*`/`weeksFromNow*` → Date range filters

The `headless` field becomes irrelevant for API mode (no browser), but won't cause issues — it's simply unused.

**Optional UI enhancement**: Add a `workerMode` field to the create/edit user form so admins can choose API vs browser mode per session. This is a nice-to-have, not required for the initial implementation.

### Step 7: Desktop App (No changes needed)
**File**: `desktop-app/src/main/embeddedBackend.ts` (no changes)

The embedded backend spawns `src/server.js` which spawns workers via `workerPool.js`. The `VISA_WORKER_MODE` env var will flow through naturally.
